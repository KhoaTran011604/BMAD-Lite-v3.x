# Story 3.2: Export Transaction Form UI

**Status:** Done
**Epic:** Export Transactions & Inventory Safety
**Created:** 2026-05-23
**Last Updated:** 2026-05-23

## Story

**As a** Warehouse Operator,
**I want** an export entry form with validation warnings,
**so that** I can quickly record farm handovers and see immediately if stock is lacking.

## Acceptance Criteria

1. Given the Export Form, When the user inputs a quantity higher than the selected material's current stock, Then the UI must display a clear "Insufficient Stock" error message in red and disable the submit button.
2. Given the Export Form, When submitting, Then it must require a "Purpose/Destination" string tag (e.g., "Field A", "Tool Repair").

### Data Models

- IExport:
  - `date`: Date (required)
  - `requesterName`: string (required)
  - `materialId`: string (FK -> Material, required)
  - `quantity`: number (required, > 0)
  - `destinationPurpose`: string (required)
  [Source: docs/architecture/data-models.md]

- IMaterial:
  - `id`: string
  - `name`: string (unique, required)
  - `type`: MaterialType ('Seeds' | 'Fertilizers' | 'Pesticides' | 'Tools', required)
  - `uom`: string (required)
  - `currentStock`: number (required, >= 0)
  [Source: docs/architecture/data-models.md]

### API Endpoints

- `GET /api/materials` - Fetches the material catalog used by the export form selector
  [Source: docs/architecture/rest-api-spec.md]
- `POST /api/exports` - Records a stock disbursement and rejects requests that exceed stock on hand
  [Source: docs/architecture/rest-api-spec.md]

### Workflow Notes

- The architecture already defines an export logging workflow where the UI submits to `/api/exports`, the API validates stock, and insufficient-stock failures return to the drawer without closing it.
  [Source: docs/architecture/core-workflows.md]

### Testing Requirements

- Maintain the project test-after strategy with focused validation coverage for stock limits and required export fields.
- Add integration-oriented coverage for route-boundary failures surfacing correctly in the form state.
- Preserve the 80% coverage target for transaction calculations and route behavior while extending UI validation coverage.
  [Source: docs/architecture/test-strategy-and-standards.md]

### Coding Standards

- Complete Type Safety: Do not use `any`; strictly type form values, query responses, and mutation payloads.
- Dual-Layer Validation: Enforce export input rules in the React form with Zod and again at the API route boundary.
- Centralized Query Keys: Use the shared query key factory for export and material cache invalidation.
- Decoupled UI Side Effects: Keep mutation hooks pure and handle drawer closing and error rendering in the UI layer.
- Negative Inventory Prevention: The frontend must block obvious over-export cases and still rely on backend enforcement as the final guard.
  [Source: docs/architecture/coding-standards.md]
