# Story 3.3: Export History Log UI

**Status:** Done
**Epic:** Export Transactions & Inventory Safety
**Created:** 2026-05-23
**Last Updated:** 2026-05-23

## Story

**As a** Farm Manager,
**I want** to browse recent disbursements,
**so that** I have a clear audit trail of who is consuming resources and where they are applied.

## Acceptance Criteria

1. Given the Transaction History page, When selecting the "Exports" tab, Then it must render all outgoing transactions sorted by date descending.
2. Given the export log, When hovered or tapped, Then it must display the staff requester name and crop purpose tags clearly.

### Data Models

- IExport:
  - `date`: Date (required)
  - `requesterName`: string (required)
  - `materialId`: string (FK -> Material, required)
  - `quantity`: number (required, > 0)
  - `destinationPurpose`: string (required)
  [Source: docs/architecture/data-models.md]

- IMaterial:
  - `id`: string
  - `name`: string (required)
  - `type`: MaterialType (required)
  - `uom`: string (required)
  [Source: docs/architecture/data-models.md]

### API Endpoints

- `GET /api/exports` - Retrieves outgoing transactions sorted by date descending for the export history feed
  [Source: docs/architecture/rest-api-spec.md]
- `GET /api/imports` - Existing import history endpoint that must continue to work alongside the new exports tab
  [Source: docs/architecture/rest-api-spec.md]

### Component Guidance

- `TransactionLogsUI` is defined as the shared UI responsibility for unified imports and exports history feeds, so Story 3.3 should extend the existing history surface instead of creating a separate export-only page.
  [Source: docs/architecture/components.md]

### Testing Requirements

- Follow the project test-after strategy with focused coverage on route-driven history rendering and interaction behavior.
- Prefer unit and integration coverage that validates sorting assumptions, tab switching, and export detail visibility without breaking the import feed.
- Maintain the 80% coverage target across route and transaction-related logic.
  [Source: docs/architecture/test-strategy-and-standards.md]

### Coding Standards

- Complete Type Safety: Strictly type query responses, export row objects, and details state; do not use `any`.
- Centralized Query Keys: Use the shared query key factory for export and import history lookups.
- Decoupled UI Side Effects: Keep query and mutation state handling separate from presentation-only UI logic.
- Negative Inventory Prevention: The history UI must reflect the backend-enforced export records accurately and must not imply successful disbursements that were rejected by stock validation.
  [Source: docs/architecture/coding-standards.md]
